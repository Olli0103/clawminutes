# Launch at login

General Settings offers a Launch at login toggle. The source implementation changes only the location of the installer-owned LaunchAgent. It never invokes launchctl, signals the helper, edits recording metadata or rewrites global settings. The UI describes the choice as applying at the next login. Real login, logout, crash and macOS background-item approval behavior remain `needs_evidence` until approved installed acceptance.

The active file is `~/Library/LaunchAgents/ai.openclaw.teams-transcribe.plist`. Turning the choice off moves that same file to `launch-at-login-disabled.plist` in the helper's private installation root. Turning it on moves it back. There is no second preference boolean in config.json. The installation receipt's `launchAtLogin` is an installation-time snapshot, not the authority for the current preference.

Apple documents that the per-user launchd loads agents from Library/LaunchAgents at login and that KeepAlive controls supervision. See [Creating launch daemons and agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html). The intended effect is to leave the already loaded job alone while changing what the next login discovers. The job's RunAtLoad and crash-supervision settings remain intact. The explicit `helper.py run` action can bootstrap the parked file without re-enabling future automatic startup. A direct Finder launch is not evidence of launchd supervision.

The helper verifies the regular file, user ownership, single link, label, exact installed executable, run arguments, installation-root environment and expected launch flags. Unknown launch triggers, malformed/oversized files, links and conflicting active/parked files block the toggle. Missing files do not get recreated by the UI. Update or repair the plugin-owned installation instead. macOS Login Items approval or external overrides can still block automatic startup; this checkbox does not verify those system grants.

A reviewed file fingerprint rejects stale settings views and replaced files. A shared lifecycle lease blocks concurrent installation while permitting a recording or processing lease to continue. A separate lock serializes preference changes. The move is atomic and refuses an existing destination. A cross-volume move fails instead of copying and deleting files. The existing file's bytes and permissions stay intact. This is not hostile-process isolation or a power-loss guarantee. An unexpected post-move state requires review and does not trigger an automatic restart or restoration.

The Python installer treats active and parked LaunchAgents as mutually exclusive. Update publishes into the selected location and includes both locations in rollback snapshots, preserving prior absence. Run and removal use the same selector. Conflicting files remain untouched. The unused inherited native installer has been removed so it cannot become a competing writer later.

Isolated native tests cover exact bytes/modes/inode preservation, recording-lease coexistence without audio capture, unchanged configuration and metadata, stale snapshots, ownership/flag/trigger guards, links, size limits and installer/pending-marker gates. A cross-language test turns the setting off through the real Swift module, executes the actual Python update entry point with OS commands/signals stubbed, verifies that it remains off, then enables the updated file through Swift. Python tests cover disabled updates, manual run, rollback, removal and conflicts. Light and dark General settings render offscreen. No installed LaunchAgent or helper is changed by these checks.

Before activation, approve and verify login with the choice on and off, a change during a live recording, manual run while disabled, abnormal exit and recovery, subsequent signed updates, and macOS Login Items approval. Check actual recording continuity and restart ownership. A file move or a healthy process alone does not prove those outcomes.
