# Gateway compatibility checks

The helper checks the authenticated ingest endpoint with GET when connecting and before each text delivery. It requires protocol version 1, text envelope version 1, structured errors, immutable completed-save behavior, a three-attempt notes budget, revision and notes-recovery support, and the verified archive contract. Missing or incompatible fields produce `plugin_update_needed` before any meeting text is sent. HTTP 200 alone cannot authorize delivery.

The Gateway performs an isolated archive check before advertising readiness or opening the real archive. A private child process writes synthetic session metadata, appends one utterance twice, writes notes and reopens the store. It verifies metadata, timestamps, speaker evidence, deduplication, the structured summary and Markdown. It also reads twice through the same three reader methods used by receipt verification and requires the scratch archive's filenames and file hashes to stay unchanged. The SDK resolver must choose a database inside the scratch directory, and that exact file must exist after writes. It calls no model and receives no user archive path.

The child has a 20-second deadline and a 16 KiB stdout limit. Its environment contains only PATH and private home/state/temporary directories, without inherited provider credentials or NODE_OPTIONS. The parent waits for child closure before removing scratch files, including after timeout or excessive output. This releases that child's SDK threads and handles. It does not stop a Gateway process. Process separation is not a sandbox for hostile SDK code, a hard memory quota or proof of a responsive live Gateway.

Successful checks are shared by concurrent callers and reused for the loaded constructor and exact source descriptor. Failed checks remain retryable as compatibility checks, but never authorize delivery or a paid model retry. The store and resolver source hashes bind parent and child imports and are rechecked after probing; changed entry files cannot reuse the preceding proof. Transitive SDK dependencies are not fingerprinted. Replacing an installed SDK still requires an approved lifecycle operation. First-use SDK loading and storage work have additional cost. Later runtime failures, host changes, schema migrations, lease behavior and cross-process ownership remain separate concerns.

The package requires plugin API 2026.9.7 or later. The runtime and helper no longer use a two-release allowlist for the v2 contract. The CI matrix includes real published 2026.9.7, 2026.9.8 and 2026.9.9 packages. Each job checks its installed package name and version before running the contracts. Current outcomes are recorded on [PR #1](https://github.com/Olli0103/clawminutes/pull/1).

A separate unlisted-version test changes package metadata to the artificial version 2099.1.1 while reusing the test SDK store. It proves removal of nominal gates, not support for a future release or every future schema. Keeping this distinct from the real 2026.9.9 job prevents a metadata fixture from standing in for release compatibility. Private SDK discovery remains a compatibility limit until a public completed-record import interface exists.

Readiness reports `archive.adapterVersion: 2`, package `sdkVersion` and `archive.verification: "isolated-readback-v2"`. The helper accepts that exact proof with a bounded, version-shaped display string. It preserves v1 handshake compatibility only for the earlier known 2026.9.7 and 2026.9.8 versions. A version number or successful HTTP response alone is insufficient. Updating or activating an installed Gateway still requires explicit approval.

Receipt verification uses the shared archive module's reader-only interface. It checks for an existing regular database, rejects leaf links and paths escaping the configured state directory through parent links, then exposes only `readSession`, `readUtterancesForSession` and `readSummary`. Missing state returns before constructing an SDK store. This guard matters: an isolated real 2026.9.7 reproduction showed that the SDK's `readOnly` option does not make mutation methods reject writes and that a reader can create missing state. The isolated probe instead checks the operations actually called against an existing archive. Filesystem checks do not provide an atomic lock against an external process removing or replacing the database afterwards; installed ownership and concurrency acceptance remain `needs_evidence`.

After a successful compatibility check, connection recovery can rearm a matching `plugin_update_needed` failure without resetting delivery or AI attempt counts. A generic Retry without that verified handshake cannot bypass the block. Model-output errors, conflicts and exhausted AI budgets remain blocked. Explicit AI recovery retains its separate confirmation and one-use request.

A meeting with a verified local archive receipt can retry its local export without a handshake or another text send. An offline Gateway cannot prevent that export recovery.

## Verification

Regressions exercise broken readback, reader mutation, escaped/mismatched database resolution, missing/linked archives, source changes, environment isolation, concurrent success reuse, failed-check recovery, unexpected/oversized output and actual deadline cleanup. Native checks accept version-metadata fixtures only with the matching v2 proof and reject inconsistent or malformed contracts. Existing no-transmission and paid-budget reconnection tests remain. The real Swift HTTP contract negotiates through the JavaScript handler and SDK before synthetic saves, revisions and receipt verification. No live helper, Gateway, credentials, recording or provider is used. See the dated results in [the review plan](review-plan.md).



## Recovery and boundary evidence

Readiness now advertises `captureGapEvidence: 2` and `maximumCaptureGaps: 4096`. The closed range schema admits the three additional native reasons `boundary_context_unverified`, `capture_timing_uncertain` and `rotation_pending`. Boundary review is recognition uncertainty, not proof of interrupted capture. Timing or handoff markers likewise do not establish missing audio; exports preserve that distinction. Every range still requires a known source/reason, safe ordered millisecond clocks within seven days and no additional fields, paths or audio. The 16 MiB request limit and separate AI input limit remain unchanged. Ranges are never silently truncated or removed to pass validation.

An envelope with these reasons or more than 32 ranges requires the expanded capability before delivery or legacy-receipt verification sends text. Reconnect must prove support for that particular envelope before clearing its compatibility cause. Earlier simple envelopes still work with the older seven-reason, 32-range contract. An unknown expanded version, missing bound or insufficient advertised bound fails closed. Verified local exports remain available offline without this negotiation. No handshake resets paid budgets or authorizes audio deletion.

The minimized validator regressions rejected both the new reason and a 40-range envelope before the fix. The actual Swift-to-JavaScript HTTP reproduction returned 422, despite the earlier boundary formatting tests passing. Those earlier tests bypassed request validation and did not establish delivery. The updated HTTP contract preserves all 40 ranges through the real handler and SDK, repeated saves, revisions and read-only receipt verification with synthetic completions. Native preflight/reconnect tests verify no transmission or state rewrite using an older handshake. Maximum-count and closed-field tests retain finite admission limits. Actual proxy forwarding and installed acceptance remain `needs_evidence`.
